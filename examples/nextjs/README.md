# nitrogql + Next.js Example

This project shows how to use nitrogql in a mid-sized Next.js app: an issue tracker with teams, projects, cycles, issues, comments and notifications.

It is also used to measure how nitrogql performs on a realistic project with fragment colocation.

## How to run

```sh
npm install --workspaces=false
npm run generate
npm run dev
```

Data is kept in memory and reset when the server restarts. There is no authentication; you are always signed in as the first user.

## Description

This app contains both client and server code in one Next.js application. It is made in a **schema-first** way: the GraphQL schema (`src/schema/*.graphql`) is written first, and client-side code and server-side code both obey the schema.

### Client side

Client-side code uses **fragment colocation**: each component declares the data it needs as a GraphQL fragment in a `.graphql` file next to it (for example `src/components/IssueRow/IssueRowFragment.graphql`). Parent components spread fragments of their children, importing them with `#import`, and each page has one query that composes the fragments of its components.

Types of GraphQL files are provided by nitrogql's [TypeScript content mapper](https://nitrogql.vercel.app/guides/typescript-content-mapper) (TypeScript 7.1 or later), so no type definition files are generated for them. Types of imported fragments are merged by TypeScript. Run the type checker with:

```sh
npm run typecheck
```

`nitrogql check` validates all GraphQL files, including spreads of imported fragments:

```sh
npm run lint-graphql
```

At runtime, nitrogql's webpack loader (`@nitrogql/graphql-loader`) turns GraphQL files into document nodes, which are used with [urql](https://commerce.nearform.com/open-source/urql/).

Shared components are in `src/components`, and pages and their components are in `src/app`.

### Server side

The GraphQL server is in `src/app/graphql/route.ts`, and resolvers are in `src/server/resolvers`. They use the `Resolvers` type generated by `nitrogql generate` with `graphql.server.config.yaml`, which checks that all resolvers are implemented correctly. The `@model` directive (from `nitrogql:model-plugin`) in the schema declares which fields are resolved from the parent object, and which types are represented by custom TypeScript types.

Run `npm run generate` again after changing the schema.

### TypeScript versions

Next.js uses the JavaScript API of the `typescript` package, which TypeScript 7 no longer provides. Therefore, `typescript` is kept at 6.x for Next.js, and TypeScript 7.1 is installed as `typescript7` for type checking (`scripts/tsc.mjs`). Type checking during `next build` is disabled in `next.config.js`.

## Measuring the cost of imported fragments

The content mapper does not expand `#import`ed fragments; TypeScript merges their types instead. To compare the cost of this with inlined fragments, run:

```sh
npm run generate
npm run bench-fragments
```

This copies the project twice to a temporary directory, inlines imported fragments into the files that use them in one copy, and type-checks both copies with `--extendedDiagnostics`.
